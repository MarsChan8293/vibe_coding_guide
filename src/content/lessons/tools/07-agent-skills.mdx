一个好 Prompt 的价值通常只活在一次对话里。Skill 的价值是把其中**稳定、可复查、可复用**的部分装进一个小目录：下一次由任何合适的 Agent 发现它、读取它，并按同一套边界做事。

按 [Agent Skills 开放规范](https://github.com/agentskills/agentskills)，Skill 的根目录至少有一个 `SKILL.md`；也可以带上脚本、参考资料和模板。Agent 先只读取 `name` 与 `description`，任务匹配时才读取正文，真正需要时再使用目录里的资源。这叫“渐进加载”。

```text
github-pages-release-check/
├── SKILL.md          # 必需：什么时候用、怎么做、何时停止
├── scripts/          # 可选：需要确定性的重复操作
├── references/       # 可选：按需读取的长文档、规范、错误对照
└── assets/           # 可选：模板、图标、样例文件
```

## 它和 MCP、AGENTS.md、脚本有什么不同？

| 东西 | 主要解决 | 最适合放什么 | 不负责什么 |
| --- | --- | --- | --- |
| Skill | “这类任务怎样可靠地完成？” | 触发条件、步骤、边界、验证、参考资料 | 提供一个外部工具本身 |
| MCP | “Agent 能连到什么工具或数据？” | 数据库、浏览器、工单系统、文件服务的连接能力 | 告诉 Agent 每一步该怎样做 |
| `AGENTS.md` / 仓库指令 | “在这个仓库里总要遵守什么？” | 技术栈、命令、目录约定、全局规则 | 只在特定任务触发的复杂流程 |
| 脚本 | “这一步怎样确定性地执行？” | 格式化、检查、转换等固定操作 | 判断什么时候该运行、如何解释结果 |

可以把它们组合：**MCP 给手，Skill 给方法，仓库指令给常驻背景，脚本给确定性。** 这是一种职责划分，不是产品等级。

<Callout type="tip" title="先别把所有知识都塞进 Skill">
  每次都相关的十行编码规范，放仓库指令；一次性的回答，留在对话；只有“会反复出现、包含判断与验证步骤”的任务，才值得做成 Skill。
</Callout>

## OpenCode 会在哪里找？

本教程的主线工具 OpenCode 已原生支持 Agent Skills。项目内推荐放在：

```bash
mkdir -p .opencode/skills/github-pages-release-check
```

然后创建：

```text
.opencode/skills/github-pages-release-check/SKILL.md
```

OpenCode 也会识别项目内的 `.claude/skills/`、`.agents/skills/`，以及用户目录中的对应位置；它把可用 Skill 的名称和描述展示给 Agent，在需要时通过 `skill` 工具加载全文。路径、字段和权限会随工具版本演进，安装前以 [OpenCode Agent Skills 文档](https://opencode.ai/docs/skills/) 为准。

## 作用域：先小后大

| 作用域 | 位置 | 适合 | 风险 |
| --- | --- | --- | --- |
| 项目级 | `.opencode/skills/` | 发布检查、仓库测试、领域术语 | 会跟随仓库共享，应审查后提交 |
| 个人级 | `~/.config/opencode/skills/` | 你的写作偏好、个人环境诊断 | 容易在不同项目误触发 |
| 团队分发 | 受控模板仓库或内部目录 | 公司规范、合规流程 | 需要版本、审核与撤销机制 |

对刚开始的团队，优先做**项目级、只读、低权限**的 Skill。把“能删除、能发消息、能部署”的动作留在明确审批之后；不要因为 Skill 是 Markdown，就忽略它可能引导 Agent 读取文件、运行命令或调用外部服务。

## 一个触发描述，决定它会不会被正确使用

坏描述：`帮助处理网站。`

好描述：`在请求发布静态站点到 GitHub Pages 前，检查构建、仓库子路径、站内链接和无障碍证据；不执行部署、不修改文件。`

前者太宽，会在不相关任务中出现；后者说清了**时机、目标、边界**。这正是 Skill 最重要的接口。
