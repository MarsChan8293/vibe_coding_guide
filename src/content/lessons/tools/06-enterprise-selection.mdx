企业选型不是让几个工具做同一道算法题。真实目标是找到一套在你的代码、网络、权限和团队能力下能够稳定交付的工作方式。

## 五个评估维度

| 维度 | 必须回答 |
| --- | --- |
| 数据 | 哪些代码、提示、日志会离开本地？保存多久？ |
| 权限 | Agent 能读写哪些路径、运行哪些命令、访问哪些网络？ |
| 模型 | 能否接入企业 OpenAI 兼容 API？模型是否可固定和审计？ |
| 审查 | 是否清楚展示 Diff、命令、测试结果并支持回退？ |
| 运维 | 配置如何分发、升级、撤销和排障？ |

## 用三个真实任务试点

选择不同风险和规模的任务：

1. **低风险**：更新文档并修复链接；
2. **中风险**：增加一个有测试的前端功能；
3. **高复杂度**：理解跨模块 Bug，但只要求分析和计划，不允许直接修改。

记录完成时间、人工干预次数、测试结果、错误类型和审查成本。不要只记录“第一次生成看起来不错”。

## 最小治理基线

- 默认从只读或工作区写权限开始；
- 密钥只通过批准的环境变量或 Secret 系统注入；
- 禁止把真实客户数据复制进公共模型；
- 所有代码修改进入 Git Diff；
- 合并前必须通过自动检查和人工审查；
- 社区 Skill、MCP Server 和插件安装前先审计源码与依赖；
- 明确谁能调整全局 Provider、权限和自动更新。

<Callout type="warning" title="不要用禁止一切替代治理">
  完全禁止通常会把使用转入不可见的个人工具。更有效的方式是提供一条审计过、能完成真实工作的默认路径，并让高风险操作显式升级审批。
</Callout>

## 本教程采用的默认结论

在“企业已有模型 API、Linux 命令行优先、需要控制数据出口”的前提下，OpenCode 是合适的教学主线。它不是唯一答案；如果你的组织已有受控 IDE 或云端 Pull Request Agent，仍应沿用相同的验证闭环。
