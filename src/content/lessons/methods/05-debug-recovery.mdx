当 Agent 生成的修改失败时，人很容易把整段日志丢回去并说“修好”。Agent 可能在没有定位根因时连续尝试，最终让问题变得更大。

## 先写复现卡片

```text
预期：
实际：
最小复现步骤：
第一次出现：
稳定复现还是偶发：
最近相关修改：
已验证不是：
第一条明确错误：
```

复现卡片强迫我们区分事实与猜测。截图可以补充，但文字步骤更适合重复执行。

## 读第一条根因，不追最后一条连锁错误

构建失败可能产生几十条后续错误。优先找到：

- 第一个非警告错误；
- 对应文件与行号；
- 在哪个命令阶段出现；
- 与最近 Diff 是否相关。

要求 Agent 先只读分析：

```text
不要修改文件。根据复现步骤、第一条错误和最近 Diff，
给出最可能的 2–3 个原因，以及验证每个原因的只读检查。
```

## 恢复层级

从影响最小的方式开始：

1. 撤销当前未保存操作；
2. 只恢复明确错误的单个文件；
3. 回退一个独立提交；
4. 在新分支或 worktree 重新尝试；
5. 涉及系统、凭证或远端数据时停止并升级处理。

<Callout type="warning" title="不要让 Agent 猜测性清理">
  避免在目标不清楚时运行递归删除、Git hard reset、清缓存或重装全部依赖。这些动作可能隐藏原始证据并删除用户工作。
</Callout>

## 修复后做回归

不仅重跑失败的那条检查，还要运行受影响区域的相关测试。路径修复可能让搜索通过，却破坏导航；依赖调整可能让本地构建通过，却改变生产锁文件。

调试的结束条件不是错误消失，而是根因得到解释、修复范围可审查、相关行为通过验证。
